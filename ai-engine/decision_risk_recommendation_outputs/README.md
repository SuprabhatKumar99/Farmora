# STEP 17 — Decision / Risk / Recommendation Outputs

This step adds the **Decision/Risk/Recommendation output layer** after
Expert 8. It preserves the established Expert 1–7, Structured Evidence
Fusion, and Expert 8 architecture.

## Architecture position

```text
Experts 1–7
     ↓
Structured Evidence Fusion
     ↓
Expert 8 — Core Agricultural Decision AI
     ↓
┌──────────────────────────────────────────┐
│ STEP 17 — DECISION OUTPUTS              │
│                                          │
│ Decision Output                          │
│ Risk Assessment                          │
│ Recommendation Formatting                │
│ Validation / Abstention                  │
│ Evidence Traceability                    │
└──────────────────────┬───────────────────┘
                       ↓
              Farmer / Extension
              Platform / Backend
```

# 1. Purpose

Step 17 converts the structured output of Expert 8 into a stable application
output contract.

It performs:

```text
Expert 8 decision
       ↓
Risk representation
       ↓
Recommendation representation
       ↓
Validation state
       ↓
Evidence traceability
       ↓
Final structured output
```

It is intentionally an output layer, not another agricultural expert.

# 2. Input

The input is the structured Expert 8 decision:

```text
diagnosis
likely_cause
disease_pest_risk
severity
affected_zone
confidence
prevention
management
treatment_recommendation
expert_or_lab_validation_required
reasoning_evidence_ids
```

It also receives:

```text
case_id
model_name
model_version
evidence_context
```

The evidence context is retained as an input contract for future integration;
Step 17 does not independently reinterpret all raw evidence.

# 3. Decision output

The output preserves:

```text
diagnosis
likely_cause
affected_zone
```

Risk is represented separately.

Recommendations are represented as structured objects.

Evidence IDs remain attached to the recommendations and final output.

# 4. Risk assessment

The risk assessor currently accepts the qualitative levels already supplied
by Expert 8:

```text
LOW
MODERATE
HIGH
VERY_HIGH
```

It also supports:

```text
medium → MODERATE
very high → VERY_HIGH
```

If Expert 8 does not provide a recognized qualitative risk:

```text
UNKNOWN
```

is returned.

This is intentional.

The implementation does NOT invent a numerical risk score.

## Why no invented score?

A numeric score such as:

```text
risk = 0.83
```

would require a validated project-specific risk model and calibration.

Without that supplied model, Step 17 preserves the uncertainty rather than
fabricating a probability.

# 5. Risk mathematics

Where a numerical confidence is supplied, it is constrained to:

```text
0 ≤ confidence ≤ 1
```

No unsupported transformation is performed:

```text
risk_score ≠ confidence
```

and:

```text
risk_probability ≠ mean(expert_confidences)
```

unless a separately validated risk model explicitly defines that relationship.

# 6. Recommendation output

Recommendations are classified as:

```text
PREVENTION
IPM
MANAGEMENT
TREATMENT
MONITORING
VALIDATION
```

The builder converts recommendation text already generated by Expert 8 into
the common schema.

It does not create new agricultural instructions.

Each recommendation contains:

```text
recommendation_id
type
action
rationale
priority
source_evidence_ids
source_model_versions
validation_required
```

# 7. No-hallucination rule

Step 17 must never manufacture:

```text
disease
cause
risk
sensor values
observations
pesticide
active ingredient
dosage
application rate
spray concentration
waiting period
laboratory result
expert result
```

It only structures information supplied by upstream components.

# 8. Treatment safety boundary

Treatment recommendations are passed through as model-provided outputs.

They are not independently expanded.

If Expert 8 supplies no actionable treatment or management recommendation,
Step 17 generates a validation placeholder:

```text
No actionable recommendation was supplied;
additional evidence or expert/laboratory validation is required.
```

This placeholder is a workflow instruction, not agricultural treatment advice.

# 9. Validation

The final output contains:

```text
validation_required
```

Validation remains required when:

```text
Expert 8 says validation is required
```

or when:

```text
evidence traceability is absent
```

This prevents the output layer from presenting an unsupported decision as
fully validated.

# 10. Evidence traceability

Expert 8 provides:

```text
reasoning_evidence_ids
```

Step 17 removes duplicates while preserving stable order.

Example:

```text
Input:
E1, E1, E2

Output:
E1, E2
```

Recommendations inherit these evidence IDs.

This allows downstream systems to trace a recommendation back to the evidence
used by Expert 8.

# 11. Model traceability

Every recommendation records:

```text
source_model_versions
```

The final output records:

```text
model_name
model_version
```

This is important because agricultural decisions may later need to be
audited against the exact model version that generated them.

# 17. Responsibility boundaries

## Experts 1–7

Produce specialized evidence.

## Step 15

Structures and compares evidence.

## Expert 8

Performs agricultural decision reasoning.

## Step 17

Formats and validates the decision for downstream application use.

## Backend

Owns:

```text
users
authentication
authorization
database
business rules
notifications
audit
workflow
```

# 18. Important architectural rule

Step 17 is not allowed to bypass Expert 8:

```text
Wrong:
Raw image → Step 17 → recommendation

Correct:
Raw inputs
   ↓
Experts 1–7
   ↓
Evidence Fusion
   ↓
Expert 8
   ↓
Step 17
```

# 21. Final no-hallucination principle

The final application output must always be traceable:

```text
Recommendation
      ↓
Expert 8 output
      ↓
Evidence IDs
      ↓
Experts 1–7 / verified sources
```

If the upstream system cannot support a conclusion, Step 17 must preserve
uncertainty rather than inventing a conclusion.

This is especially important for treatment and pesticide-related outputs.
